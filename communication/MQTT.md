# MQTT

### Message Queueing Telemetry Transport

작은 코드 공간이 필요하거나 네트워크 대역폭이 제한되는 원격통신을 위해, IoT와 같은 제한된, 혹은 대규모 트래픽 전송을 위해 만들어진 프로토콜 (1에서 10의 효율을 뽑아내기 위한 것)

- TCP/IP 위에서 동작하며, 가볍고 통신제약을 해결할 수 있다는 장점이 있다. (Wifi나 기타 방법으로 메세지 송수신 한다는 뜻)

대충 센서가 브로커에게 값을 보내면 브로커는 노트북, 폰 등에 정보 발행함. 노트북, 폰은 이를 위해 브로커 구독해둠!! 브로커님 후원이요❤️❤️❤️

- 연결 지향적
    - MQTT브로커와 연결한 클라이언트는 소켓 통신이 끊어지기 전까지 유지됨
    - Live라는 하트비트❤️와 Topic에 발행되는 메세지💌를 통해 연결 유지
    - 끊어져도 재접속 가능함
- 브로커를 통한 통신
    - 발행-구독 메세지 패턴은 오로지 브로커를 통해서만 가능, Topic 만들어서 발행하면 해당 Topic 구독자에게 메세지 발행 가능
    - 일대일, 일대다 통신이 가능
- QoS
    - 0 : 최대 1회 전송, 받는 보장은 없음, 보내고 잊어버림 (예?)
    - 1 : 최소 1회 전송, 구독자가 받았는지 불확실함 → 한번 더 전송 (핸드셰이킹 추적을 안해서 중복가능)
    - 2 : 정확히 한 번 수신 전송, 받는거 보장 (메세지 핸트셰이킹 과정을 추적했기 떄문에)
    - 이 필터는 송신자 수신자 간에만 사용됨 (TCP/IP 소켓X)
    - 뭐든 보낼 수 있음
    - 0 ~ 1 정도를 보통 사용
- 메세지 유형
    - 연결하기
        - 서버와 연결 수립을 기다리고, 다음 노드 간 링크 만들기
    - 연결 끊기
        - 클라가 해야할 일을 기다리고, 세션 연결이 끊어지길… 오매불망…
    - 발행하기
        - 클라에 요청이 전달된 직후 어플리케이션 스레드에 즉시 반환
    - 각각의 메세지의 event에 따라 MQTT 브로커가 Notification을 주어 대응할 수 있도록 함

### 토픽

메세지 발행-구독은 채널 단위로 일어남, 이를 토픽이라 함, 슬래시(/)로 구분됨

<aside>

```
company / firstFloor / SWoffice / temp
```

위에 슬래시로 구분 된 건 모두 각각의 Topic level이며, Topic level separator라고 불리는 슬래시로 구분됨

> 와일드 카드
> 

`+` : 한개의 토픽을 지정해 그 안의 여러개 토픽을 함께 지정. ex) `company / firstFloor / + / temp`

`#` : 여러레벨의 토픽을 대체할 수 있음, 무조건 마지막에만. ex) `company / firstFloor / #`

`$SYS/` : 주로 브로커의 내부메세지를 위해 사용

</aside>
